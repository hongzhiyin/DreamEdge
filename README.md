# IdeaDock 项目计划

IdeaDock 是一个内置 AI 开发能力的小工具运行框架。用户在框架中通过对话创建工具，直接使用工具，并在使用过程中继续通过对话修改界面、业务逻辑和数据结构。

本文记录需求、架构和开发顺序，供新的项目会话继续工作。第一阶段已进入实现，采用 Electron、React、TypeScript、Vite 和 SQLite；后续阶段中的设计仍是规划。

整理日期：2026 年 10 月 2 日。项目目录：`/Users/chihoyo/Project/IdeaDock`。

## 本地运行

需要 Node.js 22.13 或更新版本。首次安装依赖及 Electron 运行时需要网络；依赖就绪后，阅读工具可离线使用。

```bash
npm ci
npm start
```

应用加载独立的阅读记录工具，可添加日期、内容和分钟时长，查看累计统计，并确认删除记录。AI 面板入口已提供，当前尚未接入真实模型。

数据保存在 Electron 用户数据目录的 `data/ideadock.sqlite`，与项目源码、构建产物分开。macOS 默认为 `~/Library/Application Support/IdeaDock/data/ideadock.sqlite`。

```bash
npm run build              # 类型检查、宿主编译与独立工具构建
npm test                   # 数据持久化、隔离、业务校验和资源边界测试
npm run test:e2e            # 启动真实 Electron 窗口进行第一阶段验收
npm run build:tool -- reading-log  # 仅重建阅读工具，随后点击宿主“重新加载工具”
```

端到端测试使用临时数据库，截图保存在 `artifacts/`。实现边界、公共接口和后续起点见 [第一阶段架构](docs/architecture.md)。

## 已确定的需求

1. 框架提供一个类似网页的窗口，承载具体小工具的界面。
2. 框架能唤出 AI 对话窗口，用户通过对话修改当前小工具的功能。
3. AI 需要具备实际修改工具的能力，包括读取项目、修改代码、验证并保存结果。
4. 框架支持通过不同 API 接入不同 AI。
5. 新工具复用窗口、存储、AI 接入和开发流程，减少重复搭建 UI、数据层及运行环境的工作。
6. 每个工具可以持续迭代，用户不必每次切换到外部 AI 会话重新交代项目背景。

典型使用流程：打开 IdeaDock → 描述工具需求 → 创建工具 → 使用工具 → 唤出 AI 调整功能 → 保存后继续使用。

## 第一版的建议范围

第一阶段按个人使用的本地桌面应用实现，工具和业务数据保存在本机。后续模型通过 API 调用；云端部署仍待后续需求确定。

建议以“阅读记录工具”为验证案例：记录日期、阅读内容和阅读时长，随后通过内置 AI 增加月份筛选。

第一版优先支持使用统一前端模板、预置依赖和框架存储接口的小工具。任意语言后端、任意依赖安装、云端同步、多用户协作和工具市场留待核心流程验证后再评估。

“阅读记录工具”是用于验证架构的建议样例，不代表框架只能制作此类工具。后续可支持记账、数据分析、文件整理等场景，其中本地文件处理等能力需要额外的运行与权限设计。

## 框架与小工具的职责

| 部分 | 主要职责 |
| --- | --- |
| 框架界面 | 工具列表、工具展示区域、可唤出的 AI 对话面板、设置与修改状态 |
| 公共服务 | 本地存储、按工具隔离的数据访问、后续扩展的文件及系统接口 |
| 小工具项目 | 独立的源代码、界面、业务逻辑、数据定义、说明和构建产物 |
| AI 修改引擎 | 组织上下文、调用模型、执行受控修改、收集错误、验证和保存版本 |
| 模型适配层 | 对接不同厂商 API，统一内部的文本、工具调用、结果和错误事件 |
| 版本管理 | 候选版本、已生效版本、修改记录和恢复机制 |

框架提供稳定的公共接口，小工具调用这些接口实现自己的业务。修改某个小工具时，通常只构建和加载该工具，无须重新打包整个桌面框架。

## 小工具项目的组织方式

每个小工具作为独立项目保存，至少包含以下内容：

- 工具描述：唯一标识、名称、入口以及需要的框架能力。
- 源代码：界面、交互和业务逻辑。
- 数据定义与迁移记录：数据如何存储，以及版本升级时如何转换。
- 工具说明：已有功能、关键约定和简要修改历史。
- 构建产物及版本信息：框架可以直接加载的运行版本。

业务数据与源代码、构建产物分开存放。替换代码或重新构建不能覆盖已有业务数据。

普通工具的已保存版本应能在不调用 AI 的情况下继续运行。依赖在线服务或 AI 的具体功能除外。

## AI 修改流程

一次修改在当前工具的候选版本中进行，验证通过后再切换到新版本：

1. 用户提出需求，框架确定当前工具及当前版本。
2. 框架提供需求、项目说明、目录、公共接口文档和相关历史摘要。
3. AI 按需读取文件，提出并执行代码补丁。
4. 框架构建候选版本，收集编译错误及运行日志。
5. 验证失败时，将具体错误返回 AI，在次数和预算限制内继续修复。
6. 验证通过后加载预览，检查本次需求对应的实际行为。
7. 保存新版本及修改摘要，再将其设为当前运行版本。

第一批供 AI 调用的接口建议为：列出文件、读取文件、应用补丁、构建工具、读取错误与日志、加载预览。

模型返回工具调用请求，框架负责检查参数并执行。本地代码修改和构建不会因为接入一个模型 API 而自动具备，需要实现对应的执行器。

构建成功不等于功能正确。对于月份筛选，除了检查编译，还要验证记录筛选结果、切换月份的行为以及原有功能是否仍然可用。

修改流程需要支持取消、超时、有限重试和调用预算。失败时保留原有可运行版本，并向用户说明实际错误和已完成的步骤。

## 上下文与会话管理

每个工具拥有自己的对话记录和项目说明。切换工具时，同步切换 AI 上下文，防止把另一个工具的需求或代码混入当前修改。

每次修改时，框架应提供工具用途、已有功能、本次需求、项目目录、数据结构、当前版本、公共接口说明和近期修改摘要。相关源文件按需读取，避免每次把全部文件和历史对话都发送给模型。

项目文件和版本记录是当前状态的依据，聊天历史只提供背景。业务数据默认不必发送给模型；验证时优先使用测试数据，仅在任务确有需要时提供必要数据。

当前工具标识由框架绑定，文件及存储接口都据此限制操作范围，不能仅依赖提示词要求 AI 不要越界。

## 多模型适配

第一版先接通一家模型服务，随后接入第二家验证可替换性。

建议配置项包括厂商、API 地址、模型和密钥。内部统一处理文本输出、工具调用、工具结果、错误和用量信息；保留厂商专有的续接状态，避免丢失后续请求所需的信息。

不同服务的工具调用、流式输出、错误及上下文格式可能不同。支持自定义 API 地址并不意味着自动兼容所有服务，需按实际协议和模型能力适配。

密钥由框架的受信任服务管理，不放入小工具源码、对话上下文或可被工具页面直接读取的配置中。

## 技术栈建议

第一阶段沿用并核实了前期建议，已安装桌面和前端依赖。当前使用 Node/Electron 内置 SQLite，避免增加原生数据库扩展的构建步骤。

| 部分 | 建议 | 选择目的 |
| --- | --- | --- |
| 桌面宿主 | Electron | 承载网页界面，组织窗口和本地能力 |
| 框架及工具界面 | React 与 TypeScript | 统一组件、类型和开发方式 |
| 工具构建 | Vite 与统一模板 | 构建独立工具并加载预览 |
| 本地服务及修改引擎 | Node.js 与 TypeScript | 复用语言及代码处理生态 |
| 本地数据 | SQLite（`node:sqlite`） | 主进程通过框架接口提供持久化存储 |
| 版本管理 | Git 或项目快照 | 保存代码版本及修改记录 |

宿主、工具界面、修改执行器及模型适配层保持清晰的职责边界。第一阶段工具加载方式和公共存储契约已实现，详见架构文档。安装包制作与草稿发布流程已配置，开发者证书签名与自动更新尚未实现。

## 运行与恢复边界

- 工具页面通过有限的公共接口访问本地能力，接口验证工具身份及参数。
- AI 修改接口只操作当前工具允许编辑的文件；构建使用框架控制的命令和预置依赖。
- 窗口或进程分离不等于完整的文件系统与网络权限隔离。后续开放任意依赖、脚本或后端代码前，需要另行设计执行隔离。
- 已生效版本和候选版本分开，候选构建失败不替换当前运行工具。
- 代码恢复与数据恢复分别设计。恢复旧代码不会自动撤销数据库变化；数据结构修改需要迁移、备份和兼容性检查。

## 分阶段开发计划

### 第一阶段 宿主和手工样例

实现桌面窗口、工具展示区域、AI 面板入口和最小工具加载方式。手工制作阅读记录工具，接入框架存储接口。

验收标准：能够添加、查看并保存记录；关闭 IdeaDock 后重新打开，工具和记录仍可使用。此阶段无需真实模型即可验证宿主与工具的基本关系。

### 第二阶段 AI 修改已有工具

接入一家模型服务，实现上下文组织、受控文件操作、候选构建、错误返回和预览流程。通过对话为阅读记录工具增加月份筛选。

验收标准：用户提出需求后，AI 实际修改代码；新版本可预览和保存；筛选结果正确；原有记录保留；构建失败时旧版本仍可使用；修改可取消。

### 第三阶段 版本恢复和数据迁移

完善修改记录、版本切换、代码恢复和数据库备份。选择一个新增字段的需求验证数据迁移。

验收标准：新增字段后旧记录仍可读取；能够恢复兼容的旧代码版本；不兼容的数据变化不会被当作普通代码恢复处理。

### 第四阶段 从模板创建新工具

提供新工具入口，由 AI 基于统一模板创建第二个用途不同的工具，复用框架接口。

验收标准：第二个工具能够独立运行、保存数据和继续修改；两个工具的数据及对话上下文相互隔离；重启后都能正常加载。

### 第五阶段 第二家模型接入

增加第二家模型适配器，验证文本、流式响应、工具调用和错误处理。

验收标准：切换模型后仍能继续修改同一个工具，不需要重新生成项目或重新搭建存储层。
